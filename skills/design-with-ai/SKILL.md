# 用 AI 设计：理解优先，大胆服务获得感

> North star: **帮助用户理解文章，并留下强烈获得感。**  
> 随机种子、大胆构图、去模板感都有价值，但若妨碍阅读、扫读或带走要点，一律让路。

把材料变成有身份、可用的单页/界面/HTML 精讲。默认「文章转网页」：可接收 research-summarizer 的理解地图，也可直接读取用户材料；下游用户应感到「我真的读懂了并能用」。

---

## 北星排序（冲突时按此裁决）

1. **理解**：论点、结构、证据关系清晰可记  
2. **获得感**：读完知道自己多会了什么、下次怎么做  
3. **忠于原文**：不删论点、不造案例、不伪造成绩  
4. **大胆与去模板**：在 1–3 成立后放大差异（构图/交互，不只换皮）  
5. **装饰与动效**：仅当加强理解或节奏；否则删  

验收时先做「合上页能否复述 thesis + 模型 + 2 条带走」，再谈是否好看。

---

## 先确定边界

- 读完指定材料（含 research brief）；截断则继续读完。分清原文 / 整理补充 / 推断。  
- 明确用户、任务、场景、交付格式。文章转网页默认：**单文件、以阅读理解为先**；中文精读时保证行长、层级、对比度。  
- 报告必须保持章节↔原文要点对应。美术不能默默删论点、伪造案例，或把全文精讲摊成同质方法清单。  
- 若 brief 含「给设计的理解约束」，视为硬约束。  
- **受众**：精读页的 intended user 是「来读懂这篇、带走获得感的读者」，不是开发者、不是旁听施工过程的人。

## Discover：技术 1、2（大胆，但目标锁定理解）

### 1. 外部随机性打开方向

需要种子探索时：

```sh
python3 -c 'import secrets,string; print("".join(secrets.choice(string.ascii_letters+string.digits) for _ in range(192)))'
```

检查长度=192。种子只进私有笔记，**禁止**写入页面/公开文案。

写 2–4 个**具体**观察（重复片段、大小写节奏、数字簇、疏密），并解释如何影响**信息结构呈现**（何为主模型、何为次证据、如何扫读获得感），不只配色。禁止把种子取模映射成「赛博/极简/玻璃拟态」菜单。

随机性不能压过：可读性、语义色、可访问性、理解任务。

### 2. 提高探索野心（且筛掉「好看但不懂」）

列 6–10 个方向，**差异至少改构图或交互**。每个方向用一句话回答：

- 用户 30 秒内如何抓住核心模型？  
- 获得感区块如何被找到？  
- 会不会为了风格牺牲正文？

淘汰：同质卡片墙、纯装饰光效、为野而野导致正文难读。  
用户嫌普通时：重新抽种子并换构图/交互，而不是只换色。

收敛成设计简报：用户任务、创意母题、**理解用信息结构**、字体/颜色角色、交互、验收点（含理解验收）。

## Define：技术 3、4、5

### 3. 独立截图批评

完整流程且工具允许时：独立子代理盲评可运行初稿（先读 `references/critic.md`）。批评者**不得**拿实现理由、目标分、先前分。默认：评 → 改 → 复评。

批评提示须包含理解向问题，例如：

- 不读正文标题，能否猜出文章在解决什么？  
- 核心模型是否比装饰更醒目？  
- 获得感/行动项是否可被独立扫到？  
- 移动端是否仍能完成「复述级」阅读？

### 4. 图像

优先用原生 HTML/SVG/CSS 表达结构关系（公式、分层、对照）。生成图仅当解释概念/建立记忆点且不替代证据。禁止无内容的能量球/抽象漩涡冒充信息。

### 5. 视频可选

仅当时间/状态变化真正需要；不可用则说明并完成其余。

---

## Deliver：技术 6、7、8

### 6. 删无价值

删不增理解/行动的装饰。保留语义结构、焦点、对比、错误反馈。

### 7. 去模板

禁止五段同构「大标题+短文+卡片」。结构应镜像文章心智模型（乘积式、分层、对照、时间线、决策树等）。

### 8. 表达权

核心说明先提炼再重写；不虚构用户经历。AI 润色不叫「人手重写」。

---

## 文章转网页 — 推荐信息骨架

按理解节奏排，而非按装饰模块排：

1. **钩子 + thesis**（立刻知道这篇改什么认知）  
2. **可感知的结构模型**（图/公式/分层——页面主角）  
3. **分节深读**（每节：主张 → 证据锚点 → 所以怎样）  
4. **Discard / Keep 或常见坑**  
5. **获得感 / 行动清单**（可扫读、可带走）  
6. **出处与局限**（provenance）

---

## 必做：user-facing-only 内容审查

在发布或把 HTML 交给用户之前，**必须**按 [user-facing-only](../user-facing-only/SKILL.md) 审查可见内容（只读审查也可，但有问题要修到过关再交付）：

1. 明确：成品、intended audience（精读读者）、任务（读懂+获得感）、使用场景（打开单页/公网精读）。  
2. 把施工上下文与读者内容分开。以下内容**默认不得**出现在页面上（除非 disclosure gate 授权）：  
   - 设计种子、私有设计笔记、子代理/critic 过程  
   - 「v1/v2/v3」「我们重做了」「Auto-review」「skill 名称」等施工叙事  
   - demo/mock/sample/fixture 标签（仅因真实是演示/种子数据）  
   - 实现约束解说（「因为截图工具不可用所以…」）  
3. 以从未听过施工对话的读者视角检查渲染页。  
4. **Disclosure gate**：可见披露仅当用户明确要求、法律/安全义务、或省略会实质误导读者。出处/局限若服务于读者判断可信度，可保留；施工过程与工具故障说明不行。  
5. 发现问题：删改页面，再复查；不要只在聊天里道歉却留下施工泄漏。

## 交付验收

分开记录：**理解/获得感**、内容完整性、**user-facing-only**、视觉、功能。

理解验收（必须）：

- 陌生人能否在首屏附近说出文章要改的认知？  
- 核心模型是否比导航装饰更醒目？  
- 获得感列表是否不依赖读完全文每一字？  
- 中文精读：行长、层级、字号、对比在 1440/768/375 下可测  

user-facing-only（必须）：无施工泄漏；无未授权 demo/mock 标签；可见披露过 gate。

视觉/功能：多视口、键盘与深链、`file://` 若需要、核心内容默认可见、不作假评分或未做的盲评。

最终交付文件/链接；简述方法、检查、未满足项。大胆失败但读不懂 = 未交付。未过 user-facing-only = 未交付。

核对原文边界时读 `references/provenance.md`。
