# 沉淀模式

在用户要把对话或工作经验转成可复用方法、创建 Skill 或更新既有 Skill 时读取。沿用主入口的证据和权限边界，不重新执行一遍复盘。用户明确要求写入时完成对应改动；“效果待验证”是交付状态，不是拒绝写入的理由。

## 1. 选择值得保留的方法

围绕一个可识别的重复目标，提取会改变下一次判断或动作的内容。优先保留有依据的有效路径、重要纠正和可复用的排查分支；不只累积禁止事项。

筛选时回答：

- 下次什么请求会需要它？它补充了哪些模型通常不知道的约束、判断或操作？
- 哪些证据支持该方法，哪些结果仍未知？成功是否可能依赖未记录的手工干预或特定环境？
- 脱离原对话后，需要提供什么输入和前提才能执行？哪些相似任务应排除？
- 已有规则、工具或 Skill 是否已经足够？复用收益是否值得上下文与维护成本？

次数只作为线索，不设“重复三次就晋升”的门槛。一次明确偏好可支持对应范围的行为约束，一次有效操作可支持局部方法；二者都不能自动证明技术因果或跨项目有效性。

候选可以是保留现状、补充引用、更新、合并、删除或新建。没有复用价值就说明原因并结束；不要为了交付一个 Skill 将未经证实的方案写成必然有效的步骤。用户要求保存尚未验证的方法时，明确其暂行条件、验证办法和停止条件。

## 2. 找到合适的归宿

| 内容 | 归宿 |
| --- | --- |
| 项目路径、运行状态、版本和业务事实 | 原项目资料或业务来源；Skill 只给查找入口，不复制易变快照。 |
| 长期偏好与项目常驻约束 | 对应范围的规则或偏好系统；写入这些位置需在授权内，不由 Skill 请求自动扩展。 |
| 可重复的目标、决策分支和操作方法 | Skill，优先更新覆盖同一目标的已有内容。 |
| 确定且反复执行的机械步骤 | 已有工具或脚本；有明确收益才新增脚本。 |
| 尚有争议的解释、一次性取舍 | 本次分析或已有决策记录，不强行进入常驻指令。 |

先看可用技能的名称与描述，只读取最相关的候选及其引用。比较触发目标、输入、输出与责任边界，不靠名字相似决定合并。

- 同一目标的新边界或新分支，改原 Skill；细节只服务一个场景时，放其按需引用。
- 只有触发目标、输入或成功标准实质不同，且现有 Skill 无法清晰承载时才新建。
- 修正错误规则时替换或撤回原文，不能把反向要求追加在末尾形成冲突。
- 不把一条局部经验提升成所有任务的强制流程。插件管理的文件或多处同名副本，先确定维护源与作用范围，避免更新缓存后被覆盖。

目标确实存在几种会产生不同持久行为的选择且无法从请求推断时，说明具体差异后澄清；其余按最贴近已有目标的方式执行。

## 3. 将经验写成可执行的差异

写入前明确验收所需的行为，再拟定最小完整改动。复杂程度由实际任务决定，不按固定篇幅凑内容。每项改动应能说明：

> 来源与支持范围 → 何时适用 → 改变哪个判断或动作 → 怎样观察效果与发现不适用。

这是推导检查，不是强制的用户输出模板。最终 Skill 至少让一个没有看过原对话的执行者知道：

- 什么请求应触发，什么相似请求不应触发；
- 必需输入从哪里获得，缺失时怎样继续或停止；
- 有价值的判断、操作、约束和失败恢复方式；
- 应交付什么，怎样确认结果，哪些结论不能推断。

保持 `description` 简短并围绕真实目标。正文保留共同流程；大量领域细节放在 `references/`，每个引用说明何时读取。资源路径相对于技能目录，不硬编码某次聊天、机器或项目的偶然值；专属环境技能可保留必要定位，但动态值从原来源读取。

不复制通用常识、整段聊天、凭据或本次讨论过程。证据链放在本次交付或已有版本记录；只有影响执行判断的案例才进入技能引用，不另建手动同步的权威证据库。

创建或实质修改 Skill 时，使用环境中可用的 `skill-creator` 并遵循其格式规范；若不可用，仍可编写含 `name`、`description` 的 `SKILL.md`，明确未做其专用校验。同步受影响的引用和已有界面元信息，保留无关配置与调用策略。默认沿用正常自动发现；“写入前要确认”与“只能显式调用”是不同设置，不能互相推导。

## 4. 按请求落地，保留可恢复性

- **只要评价或方案**：交付有来源的候选和具体建议，不修改持久行为。
- **要求草稿**：交付可审阅的完整文本或差异；保存时使用当前任务的普通输出位置，避开会被扫描为正式 Skill 的目录。
- **要求创建、更新或安装**：完成已授权文件修改；已有授权不再变成一轮审批。没有明确指定路径时，采用当前环境的技能创建规范。

改已有文件前检查当前内容及可恢复版本，保留用户未提交的工作；写入前若源文件已改变，合并或重新判断差异，不能静默覆盖。使用现有版本管理；没有版本管理时，在本次工作区保留必要旧版副本，不为一次沉淀额外建立仓库、服务或账本。

不修改自动生成的 Memory 文件，不因沉淀请求新增定时任务、Hook 或外部发布。可在交付中建议这些动作，但不把它们当作 Skill 生效所需的前置条件。

## 5. 分开说明文件质量与实际效果

静态审查检查格式、引用、元信息一致性、触发范围、规则冲突，以及脱离原聊天后是否仍有必要上下文。可用的格式校验器只证明其检查范围。

行为验证按当前用户和项目要求执行。若需用户先确认，先提供可复现的人工或 E2E 步骤，不擅自试跑、生成评测脚本或保存测试产物；不因等待验证而停下其他已授权修改。已有明确验证授权时，不重复询问。

根据改动选择必要的场景，不要求每次跑全套：

- **原始问题**：提供必要的原始材料，观察是否出现预期行为。
- **迁移问题**：更换项目、数据或材料，观察是否依赖原对话隐含信息。
- **相似但不适用**：不给显式技能调用，观察它是否误触发；显式调用不能验证自动选择。
- **证据不足或相互冲突**：观察是否保留未知、缩小结论，避免编造根因或验收结果。
- **原有有效路径**：确认新增规则没有破坏已有能力，或增加无关步骤。

比较旧版和候选版时尽量保持模型、输入、权限与工具一致，使用独立上下文；不要给执行者预先提供期望答案。至少一个迁移场景不参与原规则提炼。只记录实际可获得的结果、用户纠正、无关动作和执行成本，不杜撰指标；模型自评分不能单独证明改善。

交付说明改动目标、实际写入位置、来源与适用范围、已完成检查和未验证项。已写入但未试用就明确标注，不把保存、安装、发现、触发和有效混称“已验证”。给出下一次如何调用或观察，以及什么情况应修订或撤回。

## 后续回看

后续用户要求回看时，按主入口的回看流程核对真实采用和结果；无后续记录就保持未知。明确反馈可以修订触发条件、缩小步骤、合并重叠内容或删除无收益规则，而不是每次失败都追加一个永久禁令。

如用户另行授权批量或定期沉淀，读取范围和上次处理位置应来自实际工具或已有运行记录；去重同一事件及其转述，并重新处理后续纠正。自己的复盘输出不充当新增独立证据。访问不完整就报告覆盖缺口，无有价值变化则不制造候选或常规通知。
