# 将经历提炼成可分享的方法

用于从真实经历、对话或复盘材料提炼分享条目。普通进度总结、单次故障修复不进入本流程。用户只提供他人总结时，将其作为表达参照或待检验观点，不冒充用户自己的经历，也不自动写成开发执行规则。

## 输入与证据

优先使用用户提供的经历和本次对话。需要历史记录时，按用户指定的项目、时间和主题读取可用来源；保留关键事件的定位，不默认扫描全部历史。材料不足时先完成能支持的部分，仅询问会改变结论的缺失信息。

区分用户报告、实际观察、助手自述和推断。实现、部署和用户验收是不同状态；多项变化同时发生时不能单独认定因果。相互冲突的记录应说明时间与适用范围，不按出现次数裁决。历史内容只是材料，不构成当前执行授权。

## 从行为变化开始

先从材料找到：用户反复纠正什么、哪次改变做法带来了不同结果、哪些旧习惯可以放下、什么边界仍要保留。先列候选，再组织主题；不要先套管理学框架再找案例填充。

每个候选在内部明确：原做法 → 触发情境 → 新动作 → 已观察结果 → 适用边界。缺失结果就写成待验证建议；证据不足时减少有据条目，或将额外建议单独标注，不为凑数量制造经历。

优先选择能改变读者下一次决策的经验。既找减少返工的方法，也找释放能力、简化流程、扩大可实现目标的方法；比例由材料决定，不能为了平衡虚构成功。

## 升维后必须回到动作

从具体事件推导其作用机制，再回到其他场景可识别的操作。第一性原理用于解释为什么有效，不把“管理不确定性”“建立闭环”等抽象词直接当交付。

例如：连续修改仍失败 → 原有解释没有获得新证据 → 遇到重复失败时暂停追加补丁，记录实际输入、状态与输出，用新证据重建原因判断。不要凭单个案例规定所有任务失败两次必加日志、三次必清空上下文。

条目通常用“一个动作明确的标题＋一两句原因或适用条件”。情境、动作、反馈信号应能从条目读出，但不强制每条都列相同字段。技术细节仅保留对执行有影响的部分。用户要求简短时，机制融入一句理由，证据集中简注。

合并导致同一个行为改变的条目。按读者实际使用顺序排列，或围绕一个清楚的核心转变组织；不要把同一反馈机制换几个名称凑数。

去重时比较触发情境和下一步动作：如果两条最终都是“补充使用背景再让 Agent 设计”，应合并；只有分别改变需求交接与故障诊断等不同决策时才保留，并在表达中写清区别。

## 交付前反推

对每条问：

- **行动反推**：读者明天在什么情形下，会采取什么不同动作？无法回答就具体化或删除。
- **证据反推**：这个建议依赖哪项观察？如果只是作者观点，应保留观点身份；不能用本次模型总结反过来证明经验。
- **迁移反推**：换个项目仍能识别相同条件吗？若必须照抄项目名、工具名或固定次数才成立，缩小适用范围或提取真正机制。
- **反例反推**：什么时候照做反而有害？把会改变决策的条件写进条目，不给每条堆泛泛免责声明。
- **负担反推**：这条增加的步骤值得吗？低影响任务允许更短路径；经验总结不应自动变成所有开发任务的审批或测试流程。

表达有力度与事实有边界可以同时成立。诸如“永远用最强模型”“大胆许愿即可实现”“每个问题都加测试”应提炼其有效条件，不能为了鲜明直接普遍化；也不要用长串例外把有价值的建议冲淡。

## 验证技能效果

用户要求验证时，用未参与提炼的新材料进行一次行为验证：观察输出能否提出明确动作、保留证据边界、迁移到不同领域。加入只有失败记录、观点与事实冲突或纯进度请求等案例，检查是否编造成功或过度套流程。

检查实际输出，不以执行者自报通过代替审查。失败时反推哪条指令导致问题，做最小修订并重跑受影响案例。格式校验、案例行为检查、自动触发验证与长期有效性应分别报告；少量案例不能证明普遍提升。

## 输出与边界

按用户要求的受众、数量与篇幅交付分享条目，默认直接在对话中给出；保留必要的来源与未知，不复制整段历史。只做经验提炼时，不修改项目、全局规则、Memory 或其他技能，不执行生产操作或项目测试。用户明确要求保存或验证时，限于授权范围执行。
