01
先想清楚

先用最简单的方案

一上来就搭多步 Agent，延迟和成本都涨了，效果未必更好。很多场景，一次 LLM 调用加检索和示例就够了。

做法

先试单次调用；只有当它确实不够，并且能说清多出来的复杂度换来了什么，才往上加。

方案复杂度（示意）

单次调用 + 检索
先试
工作流
不够再上
自主 Agent
最后考虑
02
先想清楚

分清工作流和 Agent

两者都叫"Agent 系统"，但控制权不同。混为一谈，就会在该写死流程的地方放手让模型乱走。

做法

路径能预先写死的，用工作流；步骤数量和顺序事先说不清的，才交给 Agent 自己决定。

工作流
代码预设路径
可预测、稳定
适合定义清楚的任务

要一致性就选它

Agent
模型自己决定路径
灵活、开放
适合开放式问题

要灵活性才选它

03
先想清楚

框架可以用，但要看懂底层

框架帮你包好了调用，也把提示词和响应藏了起来。出了问题，你看不到模型到底收到了什么。

做法

先直接调 LLM API，很多模式几行代码就能写完；用框架时，确认自己读懂它底层发了什么。

直接上框架
套模板→出问题→看不到提示词
先懂底层
直接调 API→看清提示词→需要时再上框架

04
五种工作流

提示链：拆成固定的几步

一个提示里塞太多事，每件都做不好。任务能拆成固定子步骤时，不必让一次调用全扛。

做法

把任务拆成顺序步骤，每步处理上一步的输出；中间加程序检查（gate），不合格就停下。

1
写大纲

第一次调用

2
检查大纲

程序判断是否达标

3
按大纲写正文

第二次调用

05
五种工作流

路由：先分类，再分流

一套提示应付所有类型的输入，优化了这类，就伤了那类。

做法

先把输入分类，再交给各自专门的处理流程；简单问题交给小模型，难题交给强模型。

一刀切
所有问题→同一个提示→互相拖累
路由
先分类→分给专门流程→各自优化
06
五种工作流

并行：分块或投票

一个长任务串行跑，慢；只问一次，结果也不够可靠。

做法

能独立拆开的子任务就并行跑（分块）；需要更高把握的，同一任务跑多次再投票。

A
分块
子任务同时跑结果合并

如：一路答题、一路审查

B
投票
同一任务跑多次取多数

如：多次检查代码漏洞

07
五种工作流

编排者-执行者

有些任务事先不知道要拆成几块，比如要改哪些文件，得看了需求才知道。

做法

让一个"编排者"模型动态拆分任务，分给多个"执行者"，最后由它汇总结果。

1
编排者读任务

判断要拆成几块

2
执行者分头做

每人一块

3
编排者汇总

合成最终结果

08
五种工作流

评估者-优化者

一次生成往往不到位，但人能说清"哪里不好"时，模型也能。

做法

一个模型生成，另一个模型按明确标准打分并给反馈，循环到达标为止。

什么时候值得用

1
有清楚的评估标准

能说出"好"长什么样

2
迭代确实能改进结果

反馈后答案明显变好

3
例：文学翻译、复杂搜索

需要多轮推敲的任务

用好 Agent

给 Agent 设好边界

Agent 自主行动，成本更高，错误还会层层累积。放手越多，越需要护栏。

做法

每一步从环境拿真实反馈（工具结果、代码运行）；设置停止条件，比如最大迭代次数；在沙箱里充分测试。

环境真实反馈最大迭代次数关键节点人工确认沙箱测试护栏

用好 Agent

像写人机界面一样写工具

提示词改了很多遍，工具定义却随手一写。模型用不好工具，常常是工具写得不好。

做法

给模型留足思考空间，格式贴近它在网上常见的写法；参数名和说明要清楚到新同事也能看懂；多跑例子，看它怎么用错，再改工具。

随手写
参数名含糊
要求精确计数
相对路径

模型频繁用错

认真设计
参数名一看就懂
少让模型算行号
强制用绝对路径

错误显著减少
